# 開発ドキュメント標準テンプレート

このファイルは、GitHub Issue および Pull Request の作成時に使用する標準的なひな形を定義したものです。ハーネスエンジニアリングの手法に基づき、品質と一貫性を保つことを目的としています。

### 運用ルール
- AI がタイトルや説明文を作成する際は、ユーザーが GitHub 等にそのまま貼り付けられるよう、**必ずマークダウン形式（コードブロック内）で出力する**こと。

---

## 1. Issue ひな形

### タイトル
`feat/[番号]: [日本語で要約を端的に記述]`
※例: `feat/4: 開発プロセスの標準化（Issue/PR テンプレート作成）`

### 説明文
#### 背景・目的
- [作業が必要な理由を記述]
- [解決したい課題や改善のゴール]

#### 完了定義 (Definition of Done)
- [ ] [具体的な成果物や改善指標：例・コンポーネントの行数がX行以下であること]
- [ ] [技術的要件：例・ロジックがカスタムフックに移行されていること]
- [ ] [品質要件：例・GitHub Actions (Lint, Format, Build) をパスすること]

#### 実装の進め方
1. **仕様定義**: 対象の `.md` 仕様書を作成・更新し、要件を明文化する。
2. **Co-location 設計**: 実装（.tsx/.ts）と仕様書（.md）を同一フォルダに配置する構成を整える。
3. **実装・検証**: 仕様に従い実装し、`tsc` と `lint` で品質を確認する。
4. **記録**: `CHANGELOG_featX.md` に進捗を記録し、適宜プッシュする。

---

## 2. Pull Request ひな形

### タイトル
`[タイプ]: [具体的な修正内容の要約]`

### 説明文
#### 概要
- [今回の変更で達成したことの要約]

#### 主な変更点
- [ ] [具体的な変更1：例・〇〇コンポーネントの分割]
- [ ] [具体的な変更2：例・カスタムフックの抽出と型定義の追加]
- [ ] [Co-location 対応：実装と仕様書の一体化]

#### 完了定義 (DoD) に基づく確認事項
※ Issue で定義した完了定義をそのまま転記し、チェックを入れる。
- [ ] [DoD 項目1]
- [ ] [DoD 項目2]
- [ ] [DoD 項目3]

#### 影響範囲
- [変更した主なファイルやモジュールへのリンク]
